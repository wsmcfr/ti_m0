# Firmware Directory Structure

> How MSPM0G3507 firmware code is organized in this project.

---

## Overview

This repository follows a small bare-metal layering model:

- `empty.c` is the only application entry point. It calls `SYSCFG_DL_init()`,
  then `System_Init()`, then repeatedly calls `Scheduler_Run()`.
- `User/scheduler.*` owns the 1 ms tick (`uwTick`), task table, and module
  initialization order.
- `User/App/` owns business behavior and protocol workflows.
- `User/Driver/` owns hardware-facing DriverLib access.
- `ti_msp_dl_config.*` is generated by SysConfig and should not be manually
  edited.
- `tests/` contains host-side tests for pure C logic that does not touch MCU
  registers.

Do not introduce web-style `src/`, `routes/`, `services/`, or `controllers/`
directories for firmware work.

---

## Directory Layout

```text
.
|-- empty.c                         # Firmware entry point and SysTick handler
|-- empty.syscfg                    # SysConfig source of truth for peripherals
|-- ti_msp_dl_config.c/.h           # Generated SysConfig DriverLib glue
|-- User/
|   |-- scheduler.c/.h              # Cooperative scheduler and System_Init()
|   |-- App/
|   |   |-- led_app.c/.h            # LED application task
|   |   |-- uart_app.c/.h           # UART application API and my_printf()
|   |   |-- gyro_protocol.c/.h      # Pure gyroscope frame parser/command builder
|   |   `-- gyro_app.c/.h           # Gyroscope runtime application workflow
|   `-- Driver/
|       |-- led_driver.c/.h         # PB22 GPIO wrapper
|       `-- uart_driver.c/.h        # UART0/UART1 DMA and interrupt driver
|-- tests/
|   `-- gyro_protocol_test.c        # Host-side protocol unit tests
|-- gcc/, ticlang/, iar/, keil/     # Toolchain project files
`-- docs/plans/                     # Design notes and implementation plans
```

## Module Organization

New firmware features should fit one of these existing layers:

| Layer | Responsibility | Examples |
|-------|----------------|----------|
| Entry point | Hardware init handoff and main loop only | `empty.c` |
| Scheduler | Periodic task registration and tick helpers | `User/scheduler.c` |
| App | Business behavior, protocol workflows, throttling, public module APIs | `User/App/gyro_app.c`, `User/App/uart_app.c` |
| Driver | Direct DriverLib calls, DMA state, ISR glue, GPIO/UART details | `User/Driver/uart_driver.c`, `User/Driver/led_driver.c` |
| Pure protocol | Byte-level parsing/building with no hardware dependency | `User/App/gyro_protocol.c` |
| Tests | Host-executable validation for pure logic | `tests/gyro_protocol_test.c` |

Rules for adding a module:

- Add a paired `.c` and `.h` file unless the file is intentionally private.
- Put hardware register and DriverLib calls in `User/Driver/`.
- Put periodic business logic in `User/App/`, then register the task in
  `Scheduler_Task` in `User/scheduler.c`.
- Keep pure parsers and encoders hardware-free so they can be tested on the PC.
- Update all toolchain build lists when adding a `.c` file: at minimum
  `gcc/makefile`, `ticlang/makefile`, and `iar/makefile`. Check IDE project
  files if the user builds from Keil/IAR/CCS.

## Naming Conventions

- Files use lower snake case with a layer suffix, for example `gyro_app.c`,
  `gyro_protocol.h`, and `uart_driver.c`.
- Public functions use a module prefix and Pascal-style verb phrase:
  `Gyro_AppTask`, `Uart_DriverReadPacket`, `Scheduler_GetTick`.
- Static file-scope state uses the `s_` prefix, for example
  `s_gyro_latest`, `s_uart_contexts`, and `s_pc_rx_discard_buffer`.
- Compile-time constants use uppercase module prefixes, for example
  `GYRO_PROTOCOL_FRAME_SIZE`, `UART_DRIVER_RX_DMA_BUFFER_SIZE`, and
  `GYRO_APP_PRINT_INTERVAL_MS`.
- Public structs and enums use lower snake case with a module prefix:
  `gyro_app_data_t`, `gyro_protocol_parse_result_t`,
  `uart_driver_stats_t`.
- Header guards use uppercase file names, for example `GYRO_APP_H` and
  `UART_DRIVER_H`.

## Real Examples To Follow

- `User/App/gyro_protocol.c` is the model for pure protocol code: no DriverLib,
  explicit return status, null-pointer guards, and unit-testable byte fixtures.
- `User/Driver/uart_driver.c` is the model for hardware wrappers: private
  context struct, logical port enum, ISR dispatch helpers, bounded waits, and
  error counters.
- `User/scheduler.c` is the model for periodic tasks: static task table,
  unsigned tick-difference timing, and task functions that do not block.
- `User/App/gyro_app.c` is the model for App-layer orchestration: reads from
  UART App APIs, feeds the protocol parser, caches latest data, and throttles
  text output.

---

## Anti-Patterns

- Do not put DriverLib calls directly into `empty.c` or App modules when a
  driver wrapper should own the hardware detail.
- Do not put business logic inside interrupt handlers. ISRs should capture or
  flag events and return quickly.
- Do not edit `ti_msp_dl_config.c` or `ti_msp_dl_config.h` manually; change
  `empty.syscfg` and regenerate when hardware configuration must change.
- Do not create new periodic loops outside `Scheduler_Run()`.
- Do not hide protocol parsing inside UART driver code. UART drivers move bytes;
  protocol modules interpret bytes.
